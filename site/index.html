01 · the problem

Time travel for the chat, amnesia for the side effects.

LangGraph has checkpoint time-travel. Claude's agent tooling has session resume and file checkpointing. What nobody forks is the world — the SQLite database the agent's code wrote to. Rewind the thread, and every row the agent inserted is still there.

The same gap hits eval harnesses (reset the database between runs; today that means docker teardowns and fixture reloads) and agent platforms (a database per user, forkable per attempt).

offshoot makes the database a first-class branchable object. A fork is a real, independent SQLite file — open it with stock sqlite3, no forked engine, no special VFS on the read path. Branches are cheap enough to be disposable: fork per attempt, keep the winner, let TTLs reap the rest.

Try three migrations in parallel against three forks. Promote the one whose tests pass. The demo in examples/parallel-attempts/ does exactly that — watch the recording ↗ or read an agent doing it over MCP ↗.

02 · quickstart

No server. No bucket. One binary.

cli · at rest, against a local directory
$ go build -o offshoot ./cmd/offshoot
$ ./offshoot init
$ ./offshoot create app
$ sqlite3 "$(./offshoot checkout app)" \
    "CREATE TABLE users (name); \
     INSERT INTO users VALUES ('ada');"
$ ./offshoot checkpoint app v1
$ ./offshoot fork app attempt-1
$ ./offshoot rollback app@attempt-1 --to fork
$ ./offshoot status
daemon · live capture, writer never pauses
$ offshoot serve &
$ P=$(offshoot session open app)
$ sqlite3 "$P" "INSERT INTO t \
    VALUES ('agent wrote this')"
# durable in the store; writer never stopped
$ offshoot session flush app v1
$ offshoot session status
# attempt branches reap themselves
$ offshoot fork app try-2 --ttl 2h
$ offshoot touch app@try-2 --ttl none

Same binary against a bucket: offshoot -store s3://my-bucket/offshoot init — S3, R2, Tigris, and MinIO via conditional writes. At attach time offshoot probes the store and refuses to run if compare-and-swap isn't enforced, rather than silently degrading.

Building from source (go build, above) is the fast path today. Four tagged releases so far — v0.1.0 through v0.1.3 ↗ — already carry prebuilt binaries for linux/darwin × amd64/arm64; go install github.com/sricola/offshoot/cmd/offshoot@latest resolves the moment the repo goes public, since the module path is already github.com/sricola/offshoot, not an aspirational org.

03 · how it works

Boring storage, paranoid coordination.

Every branch is a lineage of immutable LTX objects in your store: a full snapshot, then incremental segments holding only the pages that changed — the daemon's capture engine already knows exactly which those are, so a flush never diffs the database. Every sixteenth flush snapshots, so a read replays one snapshot plus a bounded chain, checksum-verified member by member. A missing or torn chain member is a loud failure, never a silently short read.

one writer
One writer per lineage, enforced by leases and epoch fencing. A writer that loses its lease is fenced: its epoch is dead, its objects unreachable by chain resolution, and it stops rather than write into a dead prefix.
real forks
Children are storage-independent. A fork seeds a fresh lineage from one materialized snapshot. Destroying a parent never harms its children — fork-spam is the expected workload, not an abuse case.
cas everywhere
Every ref update is a conditional write. Concurrent checkpoint, touch, reap, and lease operations have exactly one winner; the loser gets a clean error, never a silently lost branch.
explicit durability
Durability is a statement, not a vibe. session status reports the exact transaction id each branch is durable through. Between flushes, writes are committed to SQLite but not yet in the store — and the tool says so.
ttl reaping
Attempt branches clean up after themselves. TTL counts from the last durable write or lease renewal; a live lease is never reaped; protected branches never reap regardless.

The capture engine is validated by a torture harness: a stock sqlite3 writer is kill -9'd mid-write on roughly half of every round, while the capture engine itself is bounced — a graceful restart that exercises its resume-vs-rebase logic, not a crash — every tenth round; the replica must converge to a byte-identical dump of the source after every round or the run fails immediately. make test-torture reproduces it; the numbers above are this repo's latest run, not a historical best.

The fork numbers are the other headline numbers: 2.87s → 198ms forking a 512MB database on local disk (a reflink/clonefile object copy instead of decode-then-re-encode; ~9.3ms for the copy alone, in isolation from an unrelated size-scaling check), and 4.57s → 1.03s over S3 via a server-side CopyObject call that never downloads or re-uploads the snapshot. Full methodology and every raw number: docs/benchmarks.md ↗.

04 · the integration surface

Built to be driven by the agent itself.

pytest fixture + ts testkit

pip install "offshoot-db[pytest]" wires three fixtures — offshoot_daemon, offshoot_db, offshoot_fork — into seed-once-fork-many: one seed checkpoint, a fresh forked branch per test, TTL-backstopped teardown, pytest-xdist parallel by default. @offshoot-db/client/testkit is the same shape for vitest/jest/node:test. The full tutorial, install to CI, is in the eval-harness doc.

mcp server

One command: claude mcp add offshoot -- offshoot mcp. Seven tools with descriptions a model can act on — fork before risky work, checkpoint when tests pass, roll back when they fail. Forks expire in 24h by default, so an agent that forks and forgets doesn't leak branches forever; when a harness already has a session open on a branch, MCP rides that live daemon session instead of going through disk.

langgraph companion

ThreadForks maps agent threads to branches: checkpoint the database under the conversation's checkpoint id, and when you rewind the thread, fork the world at that exact state. examples/langgraph-rewind/ runs it end to end.

python · offshoot_fork, one branch per test
def test_agent_spends_credits(offshoot_fork):
    forked = offshoot_fork()  # fresh branch, seed's checkpoint
    conn = sqlite3.connect(forked.path)
    conn.execute("UPDATE users SET credits = credits - 10 ...")
    conn.commit()
    assert credits_now(conn) == 90  # torn down + TTL-backstopped after
python · fork a live agent's world mid-conversation
with offshoot.connect("offshoot.sock") as c:
    s = c.open("app")          # leased, live-captured checkout
    agent_writes_to(s.path)      # stock sqlite3, no wrapper
    s.flush("before-migration") # named, durable checkpoint
    c.fork("app", "main", "attempt-1", ttl="2h")

Operable, not orchestrated. A fifth surface rides alongside the four above without changing any of them: serve -http ADDR exposes a hand-rolled Prometheus /metrics endpoint, a token-authed POST /rpc, /healthz, and an /events stream (SSE) over HTTP, alongside the unix socket. Every branch reports one of six computed states — active, dirty, detached, idle, pending, error — and a checkouts-ro disk budget LRU-evicts read-only checkouts once it fills. One daemon, one host, no cluster — see the operations doc and the Kubernetes sidecar recipe for running it as exactly that.

05 · the honest part

What it doesn't do.

Infrastructure earns trust by stating its limits as plainly as its features:

  • Pre-release. The storage format and CLI may still change. Not yet recommended for data you can't regenerate.
  • Linux and macOS only. The capture path and lock probing are POSIX-dependent; Windows is unsupported in v1.
  • Not a cluster. Nodes sharing a bucket won't corrupt each other — fencing guarantees that — but there is no placement, failover, or cross-node routing.
  • Materialized forks cost real bytes. N forks of a G-byte database cost up to N×G in the bucket. That's the price of GC simplicity and parent-independence — a fork never references its parent's storage, so destroying either one never endangers the other. TTLs are the operational mitigation; reflink/clonefile locally and server-side CopyObject on S3 avoid a real re-upload when they apply, but neither reduces the bytes actually stored. Page-level dedupe is the v2 arc, if TTLs and fast-fork together turn out not to be enough.
  • At-rest checkpoints are full snapshots. Only the daemon writes incremental segments — it's the one that knows which pages changed. Checkpointing large databases in a loop? Run the daemon.
